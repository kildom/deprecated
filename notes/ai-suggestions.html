In sloppy mode, if I reference variable that does exists even in globalThis, what will happen? Is this behavior standararized? Is it diffferent between JS engines?
ChatGPT said:

Yes — this behavior is standardized, and it is different between sloppy and strict mode.

✅ What happens in sloppy (non-strict) mode

Reading an undeclared variable

If you try to read a variable that doesn’t exist (no var/let/const, not on any scope chain), a ReferenceError is thrown at runtime:

js
console.log(notDeclared); // ReferenceError

So simply accessing an undeclared name fails even in sloppy mode. That part is standardized. developer.mozilla.org

Assigning to an undeclared name

This is the part you’re likely thinking of:

js
function foo() {
    x = 42; // No var/let/const
}
foo();
console.log(x); // 42 (global variable created)

In sloppy mode, assignment to an undeclared name implicitly creates a property on the global object (globalThis.x). That’s how engines historically behaved and it’s baked into the ECMAScript spec’s environment model (“global environment’s object record”). developer.mozilla.org+1

So:

  • Reading an undeclared variable → ReferenceError

  • Assigning to undeclared name → creates a global binding/property on globalThis

This is a widely-supported behavior across all major engines (V8, SpiderMonkey, JavaScriptCore, etc.) because it’s part of the core spec model. That’s why most linters treat implicit globals as bad practice. developer.mozilla.org

💡 The fact that sloppy mode creates globals from assignments (but strict mode does not) is a key reason strict mode exists. developer.mozilla.org

🚫 Strict mode (for contrast)

In strict mode:

  • Assigning to an undeclared variable throws a ReferenceError, instead of creating a global. developer.mozilla.org

  • Reading undeclared variables still throws (same as sloppy). developer.mozilla.org

Strict mode simply disallows accidental globals.

📍 Is this behavior standardized?

Yes — both behaviors are specified:

  • Global variable creation from assignments in sloppy mode is part of the language’s abstract environment and binding model.

  • Strict mode throws instead — also required by the ECMAScript specification. developer.mozilla.org

Engines implement this consistently today. There were minor differences in very old engines decades ago, but modern engines align with the spec for this behavior.

I have 3 modules in JS A.js, B.js, C.js. A imports B, B imports C, C imports A, so it is closed loop. All the modules have some side effects (some code runs from top level scope). What will be the order they run theirs side effects? Is this standarized? Is it defined behavior? How existing engines handle that?
ChatGPT said:

Yes — this is defined behavior and standardized (for ES Modules), but the *exact order of side-effect execution in a cycle like A → B → C → A isn’t something you can pick arbitrarily — it follows a specific algorithm defined by the ECMAScript module loader and all modern engines implement it consistently. Stack Overflow+1

Here’s what you should know:

📌 1. Modules are statically analyzed and evaluated once

Before any module body runs, the module graph is built from static import/export statements. The loader traverses this graph, looks at dependencies, and prepares modules for evaluation. esdiscuss.org

During this instantiation phase, the engine:

  • Creates module records for each file

  • Sets up live bindings for exported values

  • Detects the dependency graph (including cycles)

Then it performs the evaluation phase, where side-effect code (top-level code in each module) runs. developer.mozilla.org

📌 2. Side effects run exactly once per module

Even in a cycle, a module’s top-level code executes at most once. So if you import module B multiple times (directly or indirectly), its side effects only run on its first evaluation. iO tech_hub

📌 3. In a circular cycle, order is determined by the static graph

When you have a cycle like:

css
A imports B
B imports C
C imports A

the engine will pick a root based on import resolution and then:

  1. Start evaluating that module

  2. Recursively evaluate dependencies

  3. If it encounters a module that’s already in the graph, it does not re-evaluate it and instead uses its partially-instantiated live bindings until they’re fully initialized later. esdiscuss.org

So the order you see side-effects run in practice depends on which module the loader considers the entry point. For example:

js
// main.js
import './A.js';

When loading starts from A.js, typical engines will:

  1. Visit A.js

  2. See it needs B.js → visit B.js

  3. See B.js needs C.js → visit C.js

  4. See C.js needs A.js → but A.js is already being processed

  5. Then evaluate modules in the order the loader chose as it unwinds back up

This often results in something like:

css
A’s imports discovered
B’s imports discovered
C’s imports discovered
C’s top-level runs
B’s top-level runs
A’s top-level runs

(where each top-level run is your side effects) — but the exact ordering emerges from the dependency graph and the loader’s traversal, not arbitrary timing. Stack Overflow

📌 4. Live bindings allow circular references without crash

Because ES Modules use live bindings, modules in a cycle will see references to each other’s exports even before initialization is complete. If you access a binding too early, it may be uninitialized (undefined or a TDZ error for let/const) until the module that defines it runs its top-level code. app.studyraid.com

Example:

js
// a.js
import { y } from './b.js';
console.log('a sees y =', y);
export const x = 1;

// b.js
import { x } from './a.js';
console.log('b sees x =', x);
export const y = 2;

This will typically log:

java
b sees x = undefined
a sees y = 2

because when b.js runs, x has been declared but not yet initialized. app.studyraid.com

📌 5. This behavior is standardized

Yes — how ES Modules are loaded, how cycles are handled, and how live bindings work are specified in the ECMAScript specification. All major JS engines (V8, SpiderMonkey, JavaScriptCore) follow this behavior consistently. There’s no engine-dependent random order — it’s determined by how the module graph is traversed and evaluated. esdiscuss.org

📌 6. Important practical implications

  • The actual execution order of side effects in a circular cycle depends on how modules import each other and where you start loading. Stack Overflow

  • You can depend on the fact that each module’s code runs at most once, and that live bindings will reflect updated values as initialization completes. developer.mozilla.org

  • Accessing a binding before it’s initialized can produce undefined or a TDZ error, just like topo of normal JS scopes. app.studyraid.com

📌 What strict mode actually changes or forbids

ECMAScript strict mode (standardized in ES5) changes both syntactic and runtime behavior compared to sloppy mode. Some key differences include: developer.mozilla.org

🚫 Disallowed features & semantics

Errors where sloppy silently succeeds

  • with statements become a SyntaxError. GeeksforGeeks

  • Assigning to undeclared variables throws instead of creating implicit globals. developer.mozilla.org

  • Using certain patterns like duplicate function parameters is a SyntaxError. developer.mozilla.org

  • Legacy octal numeric literals (0644) are syntax errors. developer.mozilla.org

  • Attempting to delete undeletable things (e.g., non-configurable props) throws. developer.mozilla.org

  • this inside a normal function called without an object is undefined instead of globalThis. developer.mozilla.org

Eval/arguments behave differently

  • eval() doesn’t introduce new variables in the surrounding scope. developer.mozilla.org

  • arguments no longer has magical synchronization with named parameters. developer.mozilla.org

Other safeguards

  • Cannot assign properties on primitives. developer.mozilla.org

  • with is completely forbidden. GeeksforGeeks

Strict mode is part of the official ECMAScript semantics and is required behavior in all modern JavaScript engines (Chrome/V8, Firefox/SpiderMonkey, Safari/JavaScriptCore, Node.js) — so it is standardized and consistently implemented. developer.mozilla.org

This is where it gets less precise, because there’s no central metric like “X% of web code uses sloppy-only features”. But based on common observations from the web ecosystem:

✔ Modern code tends not to rely on sloppy features

  • Bundlers like Webpack/Babel often insert strict mode automatically. xjavascript

So most actively maintained and modern libraries/frameworks (React, Vue, Angular, Node apps, etc.) already assume strict or behave fine under it.

🧠 Practical impact for your compiler

If you drop sloppy mode entirely:

📉 What will break immediately

  • Code that depends on unintentional global creation.

  • Code using with.

  • Code that relies on non-strict semantics for this or arguments.

  • Legacy numeric forms like leading-zero octals.

📈 What probably won’t break
